# 修订工作流操作手册 · 修订档案制

> **Language / 语言**：[English](revision-workflow.md) · **中文（当前）**

> 本文件定义"系统性修订工作流"（Mode L）的完整操作规则。
> 适用场景：答辩反馈、外审意见、导师批注等**多条外部意见需要端到端整合进论文**时。
> 本方法论从一次真实的答辩反馈整合实践中蒸馏而来：17 项修订档案、4 条执行 Track、
> 实际耗时为计划的 55%（5.55 天 vs 计划 10.1 天），全部闭合后形成投稿终版。

---

## 一、核心理念

**每条意见 = 一份独立的修改档案。** 不要把 15 条评审意见揉成一个"大修改任务"——那会变成一团无法追踪、无法中断恢复、无法验证完成的浆糊。把每条意见拆成独立档案后：

- 每份档案可以独立推进、独立闭合、独立返工
- 中断后从任意档案恢复，不丢上下文（ADHD 友好 + 跨对话友好）
- "完成"有硬定义，不靠感觉
- 整个修订过程本身成为可追溯的学术档案（也是 Mode K 披露的素材）

## 二、文件结构

```
_meta/修订工作流/[版本号]_[修订主题]/
├── 00_总表.md            ← 主索引 + 进度追踪 + 状态权威单一源
├── 01_[修订项名称].md     ← 修改档案（每条意见一份）
├── 02_[修订项名称].md
├── ...
└── 99_回应信.md           ← 逐条回应（见"回应信"一节；期刊修订与外审修改说明必备）
```

完成后整个文件夹归档到 `_meta/修订工作流归档/`。

## 三、修改档案 schema

每份修改档案包含五个必备部分：

```markdown
---
status: pending          # 与总表镜像同步（见"状态权威"规则）
completion: 0%
source: 张教授评议 #3     # 意见来源
triage: accept           # accept 接受 / partial 部分接受 / defend 辩护不改 / misread 审稿人误读（见"意见分诊"）
priority: P0             # P0 必须改 / P1 强烈建议 / P2 酌情
estimate: 0.5d           # 工时估计（完成后补记实际工时）
---

## 位置
[要修改的章节/节/段落的精确位置——误读类"仅回应档案"可填"全文印象/无特定段落"]

## 原文
[当前文本的相关摘录——修订执行时对照用]

## 评审意见原文
[逐字保留评审的原话——不要转述，转述会丢失锋利度]

## 方案
[如何回应这条意见：改什么、为什么这样改、不改什么（如果部分保留需说明理由）]

## 草稿
[供讨论的修订文字草稿，标注 [AI 草稿，待作者审阅]]

## 验证
[完成标准：哪些文件会变更、如何确认意见被接住]
```

## 四、意见分诊（Triage，四分法）

规划任何修改之前，先给每条意见分类。不是每条意见都值得改文——把所有意见都当"必须改"本身就是一种失败模式：它产出防御性的、臃肿的论文。四个类别：

| 分诊结果 | 改文吗？ | 回应信里写什么 |
|---|---|---|
| **接受** | 改 | 改了什么、改在哪里 |
| **部分接受** | 改，但划定边界 | 改了什么 + 为什么其余部分保持原样 |
| **辩护不改** | 不改 | 为现有文本论证，引证据 |
| **审稿人误读** | 不改——或加一句预防性澄清 | 论文哪里已经说明了相反的意思；补了什么澄清 |

分诊结果记入档案 frontmatter（`triage:` 字段）和总表。

**误读类的规则**：

- 像其他意见一样为它建一份**仅回应档案**（response-only dossier）——其"位置"字段可填"全文印象/无特定段落"。误读的意见照样建档；只是这份档案产出的是回应信文字，不是章节改动。
- **误读也是信号。** 一位合格的审稿人读错了，通常说明该处文本没能挡住那种读法。在敲定"只在回应信里辩护"之前，考虑在误读发生的位置加一句预防性澄清——比辩驳便宜，还能防住下一位审稿人。
- **作者声称"这是误读"时，先核对再采信。** 重读争议段落：文本是否真的排除了审稿人的读法？如果文本含糊到容得下那种读法，诚实的分诊是"部分接受——加预防性澄清"，不是"审稿人误读"。反谄媚规则在这里与 Mode D 中同样适用。

## 五、回应信（逐条模板）

期刊返修和国内硕博外审都要求书面回应。逐档案起草，汇入 `99_回应信.md`。每条意见一个块：

```markdown
### 意见 N（来自 [评审人]，原文照录）
> [审稿人的原话——逐字引用，不要转述]

**回应类型**：[接受 / 部分接受 / 辩护不改 / 误读 + 澄清]

**回应**：
[如改文：具体改动与位置——页码/节号，必要处引新文本。]
[如辩护：论证过程，引证据——文献、史料、论文自身的文本。无据断言读起来就是回避。]
```

**语域三原则**：

1. **尊重但不卑屈**："感谢评审专家指出这一点"说一次是礼貌，每条回应前都说一遍是噪声
2. **具体不含糊**："已按意见修改"不是回应——写出页码、节号、句子
3. **感谢真实存在的洞见，不奉承**：意见确实让论文变好了，就说出来、说清怎么变好的；不要感谢一条你马上要反驳的意见

**中文语境惯例（国内硕博外审"修改说明"）**：国内硕博外审与答辩决议通常要求一份"修改说明"——逐条编号列表，每条意见一个条目，条目末尾给出改动页码（"修改见第 X 页第 X 节"）。答辩决议各条以同样的逐条格式回应。上面的模板可直接映射到这一格式；保留评审方的原始编号。

**追溯矩阵**：总表的档案索引表兼作回应信的追溯矩阵，列依次为：**意见 → 档案号 → 分诊结果 → 改动位置 → 状态 → （可选）复审判定**。"复审判定" = 修订执行完成后，可选用 Mode D 以该审稿人的 persona 只重读改动段——检验这处修改是否真能说服提意见的那个人，而不是只让作者自己满意。

## 六、总表（00_总表.md）

总表是整个工作流的**状态权威单一源**（authoritative source）：

- 任何状态变更**从总表开始**，再同步到档案 frontmatter（档案是镜像，不是源）
- 双源不一致时，以总表为准并立即修复
- 总表 frontmatter 标注 `authoritative_source: true` + `last_review` 日期

总表必备内容：

1. **评审来源表**：谁评的、总评如何、几条意见、日期
2. **写作基线声明**：明确"唯一真相源"是哪些文件（如 `chapters/*.md`），导出物（docx/pdf）不是修订对象
3. **档案索引表**（兼作追溯矩阵，见"回应信"一节）：每行一份档案——意见摘要 / 档案号 / 来源 / 分诊结果 / 位置 / 优先级 / 工时估与实 / 状态 / 完成度 / 改动位置（执行后填写）/ 复审判定（可选）
4. **联动关系图**：档案之间的依赖与呼应（如 #04 删掉的内容要迁入 #10；#11 的"限度"节要回收 #02 埋的伏笔）。修订不是 17 件孤立的事，联动图防止顾此失彼
5. **推荐执行路径（Track 分组）**：见下

## 七、状态系统（5 态）

| 符号 | 含义 | 判定标准 |
|---|---|---|
| □ | 未开始 | 草稿都未生成 |
| ⏳ | 进行中 | 草稿已生成，未执行到章节文件 |
| 🟡 | 部分完成 | 部分子任务已落实，**剩余部分明确标注** |
| ✅ | 已完成 | **章节文件已变更 + 修改日志已记录**（两个条件缺一不可） |
| 🔄 | 已完成需返工 | 后续审计发现问题，需要二次修订 |

⚠️ "草稿写好了"不是完成。"改了章节文件但没记日志"也不是完成。完成的硬定义保护的是可追溯性。对不改文的辩护/误读类档案，✅ = **回应信条目已写好 + 总表记录了分诊理由**。

## 八、Track 分组 · 推荐执行路径

不要按编号顺序线性执行，也不要单纯按优先级执行。把档案**按章节/主题聚类成 Track**（如 Track A = 导言四项 + 全文术语，Track B = 第三章三项……），因为：

- 同一章的修订共享上下文，一起做能省掉重复的"重新进入"成本
- 章节内的联动（节首/节末呼应）必须在同一视野中处理
- 每完成一个 Track 就是一个干净的版本快照点

**每个 Track 完成时**：跑一遍相关验证（脚本 + 文风一致性），更新总表，创建小版本记录。**全部 Track 闭合时**：创建大版本里程碑文件（含统计：字数变化、新增文献、耗时估/实对比）。

## 九、修订前自检 SOP

执行涉及某位理论家的档案前，**先检查是否有对应的 perspective skill**（由 scholar-wendao 蒸馏，如 `arendt-perspective`）：

1. 有 → 用该 skill 对档案草稿做自检：概念使用是否准确？是否混淆了"理论家本人立场"与"某派 reading"？lineage 投射是否需要明示？
2. 自检发现的问题**先改档案草稿，再执行到章节**——比执行后返工便宜得多
3. 无对应 skill 且该理论家是论证承重墙 → 提议先蒸馏一个（成本约半天，多次复用）

实战验证：一次自检曾发现比导师质疑更深一层的概念错位（把日常用法的"创造=制作"误植入了理论家自己的概念分配），并提供了"派学者投射"的方法论框架来合法化借用。

## 十、作者意愿优先 · 与档案设计的"明确偏离"

档案中的方案是**计划，不是合同**。执行时作者可以改变方向（实战案例：原档案设计"压缩 30-40%"，作者执行时明确要求改为"扩张性精修"）。规则：

- 偏离必须**显式记录**在档案和修改日志中（"与原档案设计明确偏离：原因……"）
- 偏离后更新验证标准——按新方向判定完成，不按旧方案
- 遵从并记录作者明确的新方向；旧档案不能覆盖新指令。只有新方向含糊或与另一项当前要求冲突时才询问,不为已经授权的调整重复确认

## 十一、与其他模式的联动

- **输入端**：答辩/组会的录音纪要（可由 academic-meeting-notes 类工具整理）→ 提取意见清单 → 分诊 → 建档案
- **执行中**：单份档案的执行就是一次小型 Mode A/B/F；涉及理论家的先走自检 SOP（见上）
- **执行后**：每个 Track 闭合跑 Mode G（盲读核对）确认承诺-兑现没有因修订而脱节——修订常常制造新的脱节（实战案例：第 4 章新增一节后，第 5 章开头"承上"句失效）。可选跑 Mode D persona 重读，填"复审判定"列
- **输出端**：回应信由已闭合的档案汇编而成——期刊返修时它就是 response to reviewers；国内答辩/外审场景它就是"修改说明"
- **收尾**：全部闭合后，修订工作流档案是 Mode K（AI 使用披露）的最佳审计材料
